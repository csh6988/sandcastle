# Work Package and allocation lifecycle

Formal Work Packages are generated from the Technical Baseline frozen by the active Run Snapshot. Every version names one Application, one Repository, one existing `development@1` Node Run, its package contract, and producer-first dependencies. Generate producer packages before consumers; the Runtime rejects cycles, missing producers, duplicate package identities, and Application/Repository mismatches atomically.

Assignment uses active Positions frozen in the Snapshot. The Runtime filters out inactive AI members and unregistered Agent adapters, then chooses deterministically by the fewest active assignments and Position ID. Assignment creates one Node Attempt, source branch, Workspace Allocation, Runtime Interaction Session, Sandbox identity, operation key, and evidence scope. Formal packages always use `software-rnd-local-isolated-git`, `branch`, `gitRefWriteIsolation=true`, and `runtimeImportOnly=true`; there is no bind-mount, no-sandbox, `head`, or `merge-to-head` fallback.

The lifecycle is:

```text
ready -> assigned -> running -> self-check
          \-> blocked / failed
                     \-> blocked / failed
self-check-passed -> independent Code Review
                         |-> PASS -> immutable Integration authority
                         \-> CONDITIONAL_PASS / FAIL -> Defect
                                                        \-> new version + new Attempt + new allocation
```

An unmet dependency rejects assignment, so no allocation is created. Every edge reads its own exact authority rather than sharing one generic completion flag: Artifact evidence must come from an Attempt assigned to the predecessor Version (and may pin an exact Artifact Version), commit evidence is that Version's succeeded Runtime import, Contract evidence is the exact compatible Contract revision accepted by the Technical Baseline, readiness names one ready evidence record accepted by that Baseline, and manual evidence names one approved Human Approval Node Run. One frozen `development@1` Node Run owns at most one active Work Package Version. A package-bound Attempt cannot be claimed until its exact allocation is Ready and `work-package.start` records the execution transition. A failed or unknown allocation records `work-package.blocked` and blocks the Run; retry creates fresh resources.

The assigned Position and Agent adapter execute only inside the allocation's execution tree and source branch. Work Package permissions are an allowlist applied before the Execution Profile or human Permission policy. Artifacts record that actual assignment's AI member, Position, Interaction Session, Work Package, Node Run, and Attempt. A successful execution must return an exact commit, which the Runtime-owned importer validates and imports. The package remains `running` until import succeeds; tip drift records a failed import and blocks the Run without rewriting the already succeeded execution Attempt. Startup reconciliation resumes the same non-terminal allocation, projects succeeded or failed import authority back into the package and Run, and never adopts unknown directories; cleanup remains retryable and preserves import receipts.

A passing Developer self-check must include the manifest's declared commands, log references, and the exact Runtime-imported commit. Pipeline successors of a succeeded package-bound `development@1` Node stay queued until the current active Version's exact Assignment is `self-check-passed`; the self-check transaction then delegates successor release to the Pipeline Runtime. A graph-defined skipped package branch still satisfies its Join without an Assignment. The report stores structured evidence only and never creates Code Review approval or Integration authority.

Independent Code Review freezes the exact active Version, Assignment, Node Attempt, Runtime import, canonical Diff Artifact, self-check, Specs, Harness, acceptance criteria, permission and failure inputs, Reviewer Execution Profile/Secret References/provider scopes, and excluded hidden context. The Runtime resolves two distinct eligible non-producer reviewer identities: the first records the independent finding and the second performs the fresh recheck from another new Session owned by the exact manifest and bound to the same `code-review@1` Node. Both operations use the Pipeline Runtime's Node Attempt Lease/fence, Execution Fact, AbortSignal/cancel, and reconcile/reattach seams; message, Tool, usage, and terminal evidence therefore binds the Reviewer Session and aggregate Code Review Attempt. The local Reviewer Workspace adapter constructs an exact allowlisted input bundle containing only `source/`, `inputs/manifest.json`, and `inputs/canonical.diff`; it rejects extra files, symlinks, remotes, hidden Git objects, changed bytes, and executable-bit drift. This bundle is not an isolation receipt. Formal readiness comes from the actual Reviewer execution adapter, which in production accepts only a fresh Docker Sandbox whose post-launch inspection proves the real container operation ID, read-only `/review` mount, expected private HOME/cache environment, and terminal provider receipt. It also requires a context-free launcher repository, Session capture disabled, and a non-overlapping operation-local credential scope. If execution-bound isolation or credential materialization cannot be proven, the Pipeline Runtime blocks the Review Node and Run instead of falling back to bind-mount, no-sandbox, shared credentials, or shared mutable state.

The generic Review Runtime remains the authority for Topic state, findings, bounded discussion, revisions, fresh rechecks, and immutable code-kind Gate Results. Only a fresh independent `PASS` over the current exact Version, imported commit, canonical Diff bytes/hash, and both exact succeeded Reviewer execution receipts creates immutable per-package Integration authority. Each stage's JSON must exactly equal the persisted finding or recheck/Gate; successful evidence columns are frozen, the Authority stores both stage IDs/isolation hashes/result hashes, and Query revalidates them. `CONDITIONAL_PASS` and `FAIL` create a durable Defect and ask the Work Package Runtime for a fresh Version, Attempt, allocation, and Session; prior Attempts, Topics, findings, Gates, and evidence remain immutable. The rework manifest freezes the prior Defect, Gate, findings, obligation, and evidence-backed resolution matrix; a fresh `PASS` closes the tracked obligation only after citing every required obligation, finding, and resolution evidence reference, while any other package-level open Defect blocks authority. A later import, superseded Diff, replaced self-check, superseded Version, open obligation, missing execution stage, or mutated receipt makes historical authority ineligible. The shared `code-review@1` Node remains running until every current active Version has eligible authority, then persists the sorted Version, Authority, and Gate Result IDs plus a canonical `coverageHash`; Integration must consume that aggregate coverage rather than the last package result. Desktop reloads this state from the Code Review Query View and Runtime Events and does not own the workflow.

Multi-Repository Integration begins only from that exact completed Code Review coverage. The Integration Runtime copies its Run, Snapshot, Node/Attempt, Version, Authority, Gate, commit, and Diff lineage into an immutable Generation manifest. Every Repository must have one common reviewed base commit; otherwise generation creation fails before Git and the packages must return through fresh Attempts and fresh independent Review. The manifest also freezes producer-first dependencies, Contract versions, Integration conditions, and one `integration/<run-id>/g<generation>` branch per Repository. Missing dependencies, cycles, incomplete coverage, or incompatible Contract identities block before any Git effect.

Only the Runtime-owned Integration Adapter may write a generation branch. For each operation it records durable intent, applies the exact full reviewed base-to-source tree delta through an isolated temporary Git index, compare-and-swaps only the generation ref, then records the immutable receipt/final state in a new SQLite unit of work. Source-tip drift, changed request identity, symbolic or checked-out generation refs, linked Worktrees, invalid Repository roots, conflicts, or unqueryable results fail closed. Restart reconciliation returns an exact already-applied receipt when Git proves the deterministic result; unknown effects stay blocked and are never blindly resent.

After all operations succeed, the Generation manifest's exact validation checklist requires every Repository integration condition and applicable cross-application Contract to produce an append-only, hash-bound result. A Repository succeeds only after all of its frozen items pass. Runtime-owned validation and aggregate Review executors reconcile deterministic operation keys before execution; unknown outcomes block rather than resend. Cross-application failures name producer, consumer, Contract version, fixture, Runtime evidence, and responsible/candidate Work Package Versions. Any operation or Repository failure fails the whole Generation; successful partial results remain evidence and the failed branches are never continued. A fresh aggregate independent Review must bind the exact Generation manifest and integrated commits. Only unconditional `PASS` with no open Integration defect creates `passAuthorityHash`; renderer code reads this authority through `integration-generations.inspect` and uses Runtime Events only to invalidate and reload the Query View.

Versioned testing consumes only that exact `PASS` Integration Generation authority. Each immutable Test Run manifest freezes the selected Test Case revisions, exact per-Repository integrated commits, a Build Artifact carrying that exact Generation lineage, Snapshot revision, Execution Profile, Company Directory fingerprint, fixture scripts, clock, environment, capabilities, and the Runtime-owned deterministic Test-scope risk rubric derived from the Snapshot's promoted Technical Baseline. Mutable branch tips, current package state, Renderer projections, Agent self-reports, and caller-selected risk rules cannot reconstruct it. Test execution records intent before an external effect and persists terminal facts or reconciliation evidence afterward, while Pipeline Runtime remains the sole Run, Node Run, and Node Attempt writer through a narrow transition seam whose Test-specific state mapping is private to Pipeline. Explicit failed assertions fail the Test Run; missing or unknown assertions block it; both create deterministic evidence-backed Defects and obligations. A Test Run becomes downstream authority only when every required Test Case revision has paired passing public-UI and authoritative-Runtime assertions, complete correlated Test evidence, verified cleanup, and no open Test defect or obligation.

Test rework reads the persisted Defect responsibility: one Work Package returns to that package, a cross-application mismatch returns to its producer/consumer Contract, a UI/Runtime contract mismatch names its contract owner, and aggregate or unknown responsibility preserves candidate Work Package Versions for triage. Only `test.rework.create` may create the fresh Test Run and request identity while freezing the prior manifest, Defect, route, and Integration reuse decision; direct creation cannot bypass an open related Defect. Defects and obligations remain append-only with one immutable resolution, and close only from paired passing assertions and evidence on the exact fresh PASS Test Run. Changed code, integrated commits, or Integration lineage requires fresh independent Code Review and a fresh PASS Integration Generation before testing; a Test Case or fixture-only revision may reuse the exact unchanged PASS Generation, but never mutates the earlier Test Run or evidence.

The scoped Electron fixture exercises the built renderer, preload, Runtime process, Company Database, Pipeline, Artifact Registry, audit, and Runtime Events with a real BrowserWindow input event. Runtime setup uses formal Commands and handlers for prerequisite state and Artifact Versions before startup reconciliation/listening; the Electron driver has no Company Database ownership. Only allowlisted test-build execution ports are scripted: the real click sends a consultation prompt through preload, consumes scripted adapter facts, and is verified through the persisted Interaction Turn, output, audit, and cursor-recoverable Runtime Events. Fixture config, adapter scripts, and evidence are read through component-by-component symlink rejection and no-follow descriptors; bytes are inspected, hashed, and registered from the same open file. Acceptance is reconciled to a terminal fact, evidence locators are Registry-inspected safe references, cleanup proves frozen temporary resources absent, the complete authoritative Query View hash must be acknowledged, reload restores from that Query View, and the one-time fixture claim cannot be reused. Production startup rejects fixture selection outside that validated boundary.
