# Versioned Work Packages own contracts; Node Attempts own execution resources

T14 materializes Work Packages only from the Technical Baseline accepted by the active Run Snapshot. A Work Package Version is an immutable contract for exactly one Application, Repository, and frozen `development@1` Node Run, and each Node Run may have only one active Work Package Version. Initial generation requires producer-first declarations. Later versions validate the persisted Work Package dependency graph with recursive reachability rather than treating Pipeline node array order as a topological invariant. Each edge then reads its own exact authority: produced/accepted Artifact evidence from an Attempt assigned to the predecessor Version (optionally pinned to one Artifact Version), that Version's Runtime-imported commit, a compatible Contract revision accepted by the Technical Baseline, one ready evidence record accepted by that Baseline, or one named and approved Human Approval Node Run.

Concrete execution identity belongs to each assignment and Node Attempt, not to the version. The Pipeline Runtime creates the caller-identified Attempt and remains the only writer of Node Run and Attempt state. The Work Package Runtime deterministically selects an eligible active Snapshot Position with a registered Agent adapter, creates a Runtime-owned Interaction Session, and asks the T13 Workspace Runtime to plan a `software-rnd-local-isolated-git` allocation. The allocation freezes a unique source branch, allocation root, private execution tree receipt, Sandbox identity, operation key, and evidence scope. The assigned Position, AI member, adapter, permission allowlist, execution tree, and source branch are carried in the immutable Execution Request. Claiming a package-bound Attempt is impossible until that exact allocation is Ready and the package has been explicitly started. Reattachment can therefore reuse only the same non-terminal Attempt; retry or rework creates fresh writable identities.

Successful developer execution must return an exact commit from the isolated execution tree. The Pipeline Runtime records an import intent in the terminal Unit of Work, and only the T13 Runtime-owned importer may advance the allocation source branch. Import drift or failure preserves the succeeded execution Attempt but marks the package failed and the Run blocked. Only a successful import moves the package to self-check evidence collection. A passing self-check must cover the manifest commands, include logs, and bind the exact imported commit; package-bound Pipeline successors remain queued until the current active Version's exact Assignment reaches `self-check-passed`, then the self-check Unit of Work asks the Pipeline Runtime to release eligible successors. A graph-defined skipped predecessor remains satisfied without fabricating an Assignment. The report still carries an explicit non-approval marker. It does not approve Code Review or Integration; T15 and T16 retain those authorities. Runtime Events and the mounted Work Package Query View project ready, blocked, failed, assignment, allocation, and evidence state for restart-safe supervision without giving the renderer workflow ownership.
