# Technical Gate uses registered Applications and materializes the accepted Baseline once

T12 introduces a stable Project-scoped Application identity before any Application Spec revision: registration fixes its Repository reference, application key, ownership, and build/test entry points, while immutable Spec revisions only reference that identity. Technical Review binds the T11-promoted Project Spec/readiness, exact Application Spec and Cross-Application Contract revisions, and one immutable Technical Baseline Proposal; only a fresh `PASS` may atomically materialize the separate accepted Technical Baseline and append a child Snapshot revision through Pipeline Runtime. The accepted manifest includes the exact proposal and input hashes but excludes the Quality Gate Result ID; the separate Technical Gate Promotion stores that Gate identity as external metadata. The Software architect remains the producer/owner-participant and cannot review, vote, or promote its own proposal, while only the Delivery coordinator may submit promotion. Incompatible contract evidence, conditional results, and stale upstream identities remain durable blockers. This keeps Application configuration distinct from reviewed production contracts, prevents proposal/accepted identity collapse and self-referential hashes, and preserves Pipeline Runtime as the only Snapshot writer.
