# Evidence-backed Improvement proposals gate human-approved application operations

An Improvement proposal, its Human decision, and each application operation are three separate append-only aggregates. Proposal status — `draft`, `proposed`, `awaiting-human`, `approved`, or `rejected` — is a projection over the proposal's append-only revisions and its single append-only decision, never a mutable field. A revision is authored only by a bound Runtime worker presenting a verified `{ type: "runtime-worker", authenticatedBy: "runtime" }` actor; it draws its root-cause hypothesis, proposed change, impact scope, expected metrics, and validation, rollout, and rollback plan from abstract Audit, Event, Run, Defect, and Artifact evidence refs, and deliberately takes no dependency on a Statistics table, which does not yet exist. Each revision is hashed and frozen on write; correcting a proposal appends a new revision that supersedes its predecessor by id rather than mutating the frozen content.

The Human decision is the sole authority that moves a proposal to `approved` or `rejected`, and it commits exactly once. It accepts only a Runtime-injected verified `{ type: "human", authenticatedBy: "local-session" }` principal; renderer data, ACP clients, Runtime workers, and Agent statements can neither supply nor replace that authority. The renderer's decide Command input carries only the decision, reason, evidence refs, and the expected proposal-revision hash; Runtime injects the verified actor into the immutable decision and rejects a stale or mismatched hash rather than deciding against superseded content. A second decision on the same proposal fails with `IMPROVEMENT_DECISION_EXISTS`, and an application attempt on an undecided or rejected proposal fails closed with `IMPROVEMENT_PROPOSAL_NOT_APPROVED`.

Approval authorizes exactly one idempotent application operation, keyed by its operation id. The operation freezes a canonical request hash over the approved decision, its expected hash, the target kind and id, and the expected target-revision ref before any effect; replay of an identical canonical request returns the existing intent or receipt, while a changed request under the same id fails with `IMPROVEMENT_APPLICATION_ID_REUSE`. Applying a proposal to its `harness`, `spec`, `template`, or `skill-flow` target creates a new target revision — it never mutates the current Run and never auto-publishes or activates the result. Rollback creates a restoring revision and retains the applied revision beside it; the append-only application history (`applying`, `applied`, `apply-failed`, `validated`, `rollback-requested`, `rolled-back`) is never rewritten.

The finalize and rollback contracts are defined now, but their Runtime is deferred to a later T26 slice: the foundation ships only propose, decide, and apply-intent, exposing the `ImprovementApplicationEffectAdapter` and `ImprovementProposalPersistence` seams as interfaces with no concrete adapter, no runtime, and no dispatcher wiring — mirroring exactly how ADR 0051's T22 foundation shipped Release contracts before its real adapters. It adds schema v52 and event registry v20, preserving every v19 contract, and extends the existing tunnel with typed Command and Query schemas rather than a dedicated IPC channel; transport is unchanged. Runtime Events remain invalidation-only — `improvement.proposal.created`, `improvement.proposal.decided`, and `improvement.application.completed` — signaling Query Views to refresh without carrying aggregate state.
