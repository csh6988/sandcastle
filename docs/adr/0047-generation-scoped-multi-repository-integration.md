# Multi-Repository Integration is generation-scoped and receipt-driven

The Runtime consumes only the exact completed `code-review@1` coverage payload and freezes it into one immutable Project-level Integration Generation manifest. Every participating Repository freezes one common base commit, one `integration/<run-id>/g<generation>` branch, approved source commits, producer-first dependencies, Contract versions, and Integration conditions. All reviewed authorities for the same Repository must share that base; a mismatch blocks before any Git write and requires fresh Work Package Attempts from one common base plus fresh independent Code Review. Missing dependencies, cycles, incomplete coverage, and Contract mismatches also fail closed before an Integration operation is persisted or executed.

The Runtime-owned Integration Adapter applies the exact full `baseCommit -> sourceCommit` tree delta through an isolated temporary Git index and advances only the generation ref with compare-and-swap. It never checks out or writes the Developer source branch, current user branch, Target branch, Release target branch, or an arbitrary ref. Canonical Repository roots, source and generation refs, source tips, exact commits, linked Worktrees, symbolic refs, and Git common-directory identity are validated before each effect. Operation execution follows durable intent, external Git effect, then receipt/finalization in separate SQLite units of work. Identical replay returns the first authoritative receipt; changed request identity conflicts; restart reconciliation proves the exact deterministic result from the generation ref or remains blocked when the effect cannot be proven.

Any Git conflict, unknown result, Repository validation failure, cross-application Contract failure, or aggregate review failure records an Integration defect and prevents the whole generation from becoming downstream authority. The manifest freezes an exact validation checklist derived from every Repository integration condition and applicable cross-application Contract. Validation results are append-only, hash-bound evidence; a Repository succeeds only when every frozen item passes. Runtime-owned validation and aggregate Review executors reconcile their deterministic operation keys before execution, so restart never requires an operator to submit a result Command or blindly resend an unknown effect.

Successful partial Repository results remain evidence only. Recovery creates a fresh generation and fresh generation branches from the frozen bases; the Runtime never repairs or continues a failed mixed generation. After every Repository validates, a fresh aggregate independent Review must bind the exact manifest and integrated commits. Only an unconditional aggregate `PASS`, with no open Integration defect, creates the immutable `passAuthorityHash` consumed by later Test and candidate stages. Pipeline Runtime remains the sole Run, Node Run, and Node Attempt writer; renderer state is rebuilt from the authoritative Integration Query View and Runtime Event cursor.
