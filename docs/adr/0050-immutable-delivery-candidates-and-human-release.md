# Delivery candidates and Human release decisions are separate immutable authorities

The Delivery Runtime assembles one immutable Delivery candidate only from the exact downstream authority of a frozen Delivery Candidate Input. The candidate canonical manifest copies that authority's exact Candidate Input and Gate hashes together with the frozen Product, Technical, Work Package, Code Review, Integration, per-Repository commit, Artifact Version, Contract, Test, Snapshot, risk, environment, and evidence lineage. It is bound to the current claimed `delivery-candidate@1` Node Attempt and Lease; Pipeline Runtime remains the sole writer that moves the Run to `waiting-human-release`. Identical assembly replays the first candidate, changed requests conflict, and changed upstream authority requires a new Input, Gates, and candidate rather than mutation.

The candidate and Human release decision are separate immutable aggregates. Candidate state is a projection over one append-only decision and later same-lineage candidates: only an unaccepted candidate may be projected as superseded, while an accepted candidate is terminal. Human release accepts only a Runtime-authenticated `{ type: "human", authenticatedBy: "local-session" }` principal through the typed Command tunnel. Renderer data, ACP clients, Runtime workers, Agent statements, generic Human Approval, and Gate reviewers cannot supply or replace that authority. Accepted, rejected, and changes-requested decisions preserve their reason and evidence and commit with audit, Runtime Event, receipt, and Pipeline transition in one SQLite unit of work.

Acceptance completes the Run and creates a separate immutable downstream authority containing only the exact candidate, decision, Candidate Input, Gate, Integration, Repository commit, Artifact Version, Run, and Snapshot identities and hashes. It does not name a destination, write a Git ref, export an Artifact, merge, deploy, or create a Release operation. Rejection moves the Run to `release-rejected` and requires an explicit fork for continuation. Changes requested within the frozen Product Baseline, Repository, and Pipeline boundary block the same Run for traceable rework; a boundary change uses the existing child Run fork seam and supersedes the parent. This keeps release intent independent from later T22 destination effects and prevents either aggregate from becoming a mutable release checklist.
