# Versioned Test Runs consume exact Integration authority

Test Runs consume one exact immutable `PASS` Integration Generation, including its manifest hash, `passAuthorityHash`, reviewed coverage lineage, aggregate Review evidence, and per-Repository integrated commits, then freeze that authority together with Test Case revisions, build, Snapshot, Execution Profile, fixture, environment, evidence policy, and the deterministic Test-scope risk policy, factors, computed tier, evidence, and hashes. A Build Artifact is eligible only when its producer lineage names that same PASS Generation and exact integrated commits. The Runtime derives a fixed risk rubric from the Technical Baseline promoted by the frozen Snapshot, uses the highest structured `riskTier` among every Work Package Version frozen by that PASS Generation as the minimum Test-scope tier, and rejects a missing or invalid tier, caller-selected rules, or incomplete factors. A Test Case coverage omission therefore cannot lower risk authority before it is rejected. Runtime exposes the validated risk unchanged in downstream PASS authority so T18 never reconstructs it from mutable state. Runtime must not reconstruct a Test input from a mutable branch tip, latest Generation, current Work Package state, Renderer projection, or Agent statement; changed code or Integration inputs require fresh Code Review and Integration authority, while a fixture or Test Case revision change may create a fresh Test Run against the same unchanged Generation.

Pipeline Runtime remains the sole writer of Department Run, Node Run, and Node Attempt state. Its Test-specific SQL and state mapping live in a private Pipeline collaborator behind the existing narrow transition seam, while the Test module owns Test Run manifests, durable execution intent/fact/receipt reconciliation, paired UI/Runtime assertions, evidence, defects, and downstream PASS authority. Reconciliation persists its intent, Test state transition, Runtime event, audit record, and receipt through the transaction-aware worker unit of work. Assertion results persist immutable UI and Runtime observations, derive their statuses by canonical comparison with the frozen expected values, and include those observations in the result hash. Before terminalization, Runtime constructs the complete deterministic union of failed, unknown, and missing required assertions: explicit failures make the Test Run `failed`, while any missing or unknown member makes it `blocked`, and every member creates its evidence-backed Defect and obligation. Unknown or non-terminal external effects likewise block for reconciliation instead of being blindly resent or converted into a fabricated failure. Runtime-generated assertion identities use the injected deterministic ID source so equal seeds and clocks reproduce equal records.

A failed, blocked, or cancelled Test Run may create only a fresh rework Test Run through `test.rework.create`; direct Test Run creation cannot bypass an open related Defect. Rework-of-rework recursively unions every unresolved ancestor, current, and responsibility-related cross-Generation Defect and obligation in the same Project. Relatedness follows frozen Work Package identity across Versions, producer/consumer Contract identity across Contract versions, UI/Runtime ownership within the same Test Case ancestry, and aggregate/unknown candidate Work Package lineage, rather than treating every historical Project Defect as related. For every scoped Defect, the Runtime freezes its originating Test Run and Integration Generation, original revision/assertion/result hash, persisted responsibility route, and explicit successor revision/assertion mapping. Successors must belong to the same Test Case ancestry, so a renamed assertion can be selected deliberately while an unrelated reused assertion ID cannot satisfy closure. One exact fresh PASS Test Run atomically creates the immutable resolutions for the entire transitive frozen scope; direct creation and downstream authority reject missing closure, partial closure, scope drift, or a resolution from another run. Changed code or Integration lineage requires fresh T15 Code Review and T16 PASS Integration authority; a Test Case or fixture-only revision may reuse the exact unchanged PASS Generation, but receives fresh Test Run and request identities and never rewrites historical evidence.

The scoped Electron fixture proves this contract through the built renderer, preload bridge, Runtime child process, Company Database, Pipeline, Artifact Registry, audit records, and Runtime Events. Runtime setup creates the prerequisite Product, Technical, Work Package, Code Review, Integration, and Artifact authority through formal Commands and registered handlers before reconciliation or listening; the driver never opens the Company Database or registers Artifact Versions. A real BrowserWindow click sends a consultation prompt through preload, consumes the scripted adapter facts, and proves the resulting Interaction Turn, output, audit, and cursor-recoverable Runtime Events before assertion evidence is accepted. Assertion evidence must carry the consumed token for the exact `test-runs.inspect` query and Test Run, authenticated consumer/principal, completed acknowledgement receipt and audit/effect chain, authoritative Query View hash, and sequence. Terminal materialization validates the exact acknowledged predecessor token selected by the adapter before the same atomic fact unit of work advances execution state; an older token remains invalid even when it names the same View. Fixture files are opened descriptor-relative from the captured root, with no-follow directory opens for every ancestor and a no-follow leaf open; Python startup must prove `O_NOFOLLOW`, `O_DIRECTORY`, and descriptor-relative `os.open(..., dir_fd=...)` support, otherwise the fixture emits a stable capability failure and exits nonzero without selecting an unsafe fallback. The bytes are inspected and hashed from the held leaf descriptor before entering Artifact registration. Initial cleanup requires every frozen target to exist, caches no receipt until every identity has been verified and every quarantined target deleted, and only then permits idempotent replay. Cleanup atomically renames the exact Repository, Worktree, or whole fixture root into a private quarantine, verifies the moved identity/fingerprint, and deletes only that quarantined object; a replacement created at the original path is never deleted. Registry-inspected evidence locators and cleanup prove the frozen resources absent, reload restores from the Query View, and the one-time launch claim cannot be reused. Scripted adapters remain confined to allowlisted test-build execution ports and cannot be selected by a production renderer, ACP command, or ordinary environment variable. Schema version 48 is adopted only when every Test table, index, and trigger exactly matches the normalized reference manifest; missing, altered, or extra Test schema objects fail the migration transactionally.
