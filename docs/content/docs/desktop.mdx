## Company workspace

Sandcastle Desktop opens a persistent Company Runtime workspace. The Runtime owns configuration, Runs, Snapshots, audit records, and event replay; Renderer reloads reconnect to that same local state.

## Windows distribution

Desktop v1 supports Windows x64 as a first-class build target. On Windows,
`npm run dist:windows` creates an NSIS installer and the unpacked
`release/win-unpacked` application. CI starts the unpacked `Sandcastle.exe` on
`windows-latest` and runs the same Company Runtime BrowserWindow and packaged
smoke used by the other desktop platforms before uploading the unsigned x64
installer. ARM64, Microsoft code signing, and auto-update are separate release
gates.

## Agents

The Agents page lists formally registered local coding Agents by stable ID. Detection records installation status, version, executable path, capabilities, and detection time. The **Test Agent** action performs a safe adapter-specific probe without creating a Run, changing Git, writing project files, or persisting raw command output. Claude Code, Codex, and Pi use ephemeral or non-persistent non-interactive prompts; adapters without a verified prompt contract use a capability probe.

## Skills

The Skills page discovers `SKILL.md` files from the default local roots and any directories you add. Only stable references, source paths, and SHA-256 fingerprints are stored; Skill bodies are not copied into the Company database. A Skill can declare comma-separated `required-capabilities` in its frontmatter; Desktop displays those declarations as warnings without enforcing an Agent/Skill matrix. Skills can be searched with ordered fuzzy matching, reveal their source reference on demand, and move through discovered, enabled, unavailable, and archived states.

## Positions and Departments

Each Position has an AI Member identity, a default Agent, and a set of enabled Skills. The Position editor saves those settings together and shows only enabled Skills. Department Overview is read-only; Department Settings groups basic settings, run environments, artifact contracts, and non-sensitive Secret References behind one bottom **Save department** action. Archive operations remain explicit destructive actions.

## Run history

When a Run starts, its Snapshot records the resolved Agent and whether it came from the Position default or a temporary override. It also records each Position Skill reference and its fingerprint/version, so historical Runs remain explainable after local Agent or Skill installations change.

## Review Topics

The Company Runtime owns Review Topic state, immutable independent findings, append-only resolutions, bounded discussion rounds, exact revisions, fresh re-review votes, and the final Quality Gate Result. Topic creation freezes the strict input manifest/hash, participant eligibility, reviewer quorum, budget, and stop policy. Owner-participants and moderators may respond but never submit findings or vote; the reviewed producer is also excluded from reviewer eligibility.

Every re-review vote uses a new independent Interaction Session. Final quorum must include at least one eligible reviewer who did not submit an initial finding. Any `FAIL` vote fails the gate, otherwise any `CONDITIONAL_PASS` remains conditional, and only unanimous `PASS` votes with no unresolved blocking finding satisfy downstream production contracts. Budget exhaustion records an immutable `FAIL` result and escalation evidence instead of continuing an unbounded discussion.

After exact PASS Test Runs are available, the Runtime can freeze a Delivery Candidate Input containing their complete Product, Technical, Work Package, Code Review, Integration, Repository commit, Artifact, Contract, Snapshot, risk, environment, and evidence lineage. Independent Security and Operability gates bind their inputs and results to that exact manifest hash. The Reviews view displays only authoritative Candidate/Gate Query Views; Runtime Events trigger a reload of those views, and downstream authority remains blocked until both gates are PASS with no open Defect or obligation. Delivery candidate creation and the human release decision remain separate later actions.

Product Review is bound to one exact Product Baseline and Project Spec Revision/hash. Eligible reviewers classify each Product Finding as scope-preserving or scope-changing; a scope-changing Finding permanently blocks promotion in that Run even if an owner or moderator later rejects or resolves it, so continuation requires a newly confirmed Product Proposal and child Fork. Readiness checks are immutable evidence, blockers keep the Run blocked, and only a `PASS` Product Gate can atomically append the accepted Spec/readiness references to a new child Snapshot Revision.

Technical Design starts from explicit Project-scoped Application registrations. Each immutable Application Spec Revision remains subordinate to the promoted Project Spec, and each Technical Baseline Proposal freezes the exact readiness, Application Spec, and cross-Application contract version/hash inputs reviewed by independent participants. The Software architect owns the proposal but cannot vote or promote it; incompatible contract evidence and conditional results remain blocking, while only a fresh `PASS` lets the Delivery coordinator atomically materialize a separate accepted Technical Baseline and append it to the next child Snapshot Revision.
